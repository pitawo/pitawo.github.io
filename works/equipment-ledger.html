備品貸出管理アプリ

2026-08 Python / Flask Socket.IO Claude Code

デモを触る GitHub で見る

しばらく使われていないと、開くまで数秒かかることがあります。

なぜ作ったか

機材を何人かで共有していると、「今どれが空いているか」が誰にも分からなくなります。紙やチャットで管理すると、借りたまま返却の記録が抜けたり、同じ日に二人が同じものを予定していたりします。

一覧を開けば空き状況がすぐ分かり、予約が重なったらその場で断ってくれる状態にしたかったので作りました。

どう作ったか

Flask で作りました。画面は一覧と予約フォームの1ページで、貸出・返却・設定変更のたびに Socket.IO で全員の画面を更新します。データは JSON ファイルに保存し、操作のたびに書き込みます。

できること

  • 予約 — 備品と期間と目的を指定する。同じ期間に別の予約は入れられない
  • 稼働状況 — 利用可能／貸出中を一覧表示。予約は「利用中／これからの予約／終了済み」に分かれる
  • 備品マスター — 追加・改名・削除
  • ログイン — メールとパスワード。パスワードはハッシュ化して保存する
  • 見た目 — 備品ごとに、名前から判定した線画アイコンを表示する。当てはまる名前が無ければ共通のアイコンになる

詰まった点と、直したこと

このアプリで一番危なかったのは、説明に書いてある安全装置が、実際には効いていなかったことでした。

予約が入っている備品を消せてしまう

「貸出中の備品は削除できない」と説明に書いていました。実装も、削除の前に状態を調べる形になっていました。

ところがその判定は「今日が予約期間の中にあるか」しか見ていませんでした。つまり来週の予約が入っている備品は「空き」と判定され、予約ごと削除できてしまいます。消えたことは予約した人には伝わりません。

判定を「今日以降に終わる予約が1件でも残っているか」に変え、消せなかったときは理由を画面に出すようにしました。

この不具合は、最初に書いたテストでは見つかりませんでした。削除に渡すパラメータ名を間違えていて、削除処理そのものが実行されていなかったからです。「削除できないこと」を確かめるテストが、何も起きていないことを確かめて通っていました。名前を直した瞬間に、備品が消えました。

説明に書いてある機能が、実装のどこにも無かった

「毎日決まった時刻に自動保存する」と書いてあり、そのためのライブラリも依存に入っていました。実装を探したところ、呼び出しが1か所もありませんでした。書いたつもりで終わっていたわけです。

説明から削除し、依存も外しました。代わりに、実際に動いている保存の仕組み（操作のたび・終了時・手動）だけを書いています。

本番でだけ起動に失敗する

手元では問題なく動いたのに、公開すると起動直後に落ちました。

ImportError: Entry point ('gunicorn.workers', 'eventlet') not found

手元で使っていた起動方法と、公開先で使われる起動方法が違っていました。手元は開発用サーバー、公開先は gunicorn 経由です。手元では通らない経路が本番にだけあります。

リアルタイム更新の方式を、追加のライブラリが要らないものに変えました。依存が1つ減り、環境の違いに左右されにくくなっています。

この修正が、思わぬところで効きました。今回 Cloud Run に移すとき、YouTube リサーチシステムはアプリ側を7箇所直すことになりましたが、このアプリは Dockerfile を書いて依存の版を固定しただけで載りました。理由ははっきりしています。ここで eventlet を切り離して依存を1つ減らしたことが、そのまま次の引っ越しの下準備になっていました。1つの本番環境で先に払った代償が、別の本番環境への移行を楽にしました。

登録しないと何も見えない

公開して気づきました。訪問者が最初に見るのはログイン画面で、アカウントを作らないと中身が分かりません。

「登録せずにデモを見る」ボタンを追加しました。ログインフォームを何も入力せずに送っても、同じ入口に入れるようにしています。画面右上には「デモとして閲覧中」の表示を常に出し、本物のログインと見分けられるようにしました。

ここでもう1つ、公開するアプリで、触らせたいけど壊されたくないという問題にぶつかりました。見学者にも予約や返却を実際に操作してもらいたいものの、誰かの本物の予約データを見学者が消せてしまっては困ります。

見学者が来るたびに、その人専用の使い捨てのデータ置き場をサーバー上に作り、そこにサンプルデータを渡すことにしました。見学者の操作はその置き場の中だけで完結し、保存も他の利用者への通知もしません。本物のデータには、見学者の操作が一切届かない構造にしました。

ここから学んだこと

「書いてあること」と「動いていること」は、確かめるまで別物でした。このアプリでは3回それを踏みました。説明にある安全装置が効いていない、説明にある機能が存在しない、手元で動くものが本番で動かない。どれも画面は正常に見えていました。

もう1つは、テストが通ったことと、テストが検証できていることは違うという点です。パラメータ名を1つ間違えただけで、テストは「何も起きていない状態」を成功として報告し続けました。テストを書いたら、一度わざと失敗させて、本当に見たいものを見ているか確かめるようにしています。

3つ目は、Cloud Run への移設で踏んだ、「一部を見て全体を判断した」という失敗です。リアルタイム更新が本番でどう動いているかを調べたとき、最初のアクセスログだけを見て「ポーリングだけで動いている」と結論しました。実際は Socket.IO がポーリングで接続したあと WebSocket に昇格する仕組みで、接続直後だけを見ると、まだ昇格前のポーリングしか映りません。時系列でログを追って、ようやく WebSocket に切り替わっていたことが分かりました。「書いてあることと動いていることは別物」の親戚のような失敗で、今度は「動いている全部を見ないと判断できない」ということでした。

4つ目は、同じ移設作業のなかで、測ったものが違うのに同じ名前で並べていたという失敗です。起動待ちの時間として計測した数字は、/guest へのリダイレクトという、ほぼ処理のないレスポンスへの応答時間でした。「サーバーが応答するまで」という同じ言葉で括ると、中身が違うものまで同列に見えてしまいます。

公開について

Google Cloud の Cloud Run で公開中です。元は Render の無料枠で動かしていましたが、しばらくアクセスがないとスリープし、管理画面にも「無料インスタンスは停止し、リクエストが50秒以上遅れることがあります」と表示される状態でした。企業リサーチシステム・YouTube リサーチシステムと同じ理由で、こちらに移しました。Render 側は削除ではなく停止（Suspend）にしてあるので、URL 自体は残っています。

18分26秒アクセスがなかったあとに開いたところ、サーバーが応答するまで実測で1.89秒でした。以前の Render では、しばらく使われないと停止し、起動に50秒以上かかることがありました。

永続ディスクを付けていないので、再起動すると入力したデータは初期状態に戻ります。見学で触ってもらう分にはそのほうが都合がよいと判断しました。移設後に見学モードで予約を1件作り、18分放置してから開いたところ、予約は消えてサンプルの状態に戻っていました。サーバーのログにも、アプリが「サンプルからデータファイルを作成しました」という記録が2回残っていました。仕様どおりに動くことを、実際に確かめられました。
