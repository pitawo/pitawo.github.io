YouTube リサーチシステム

2026-08 Python / Streamlit YouTube Data API v3 / SQLite Claude Code

アプリを開く GitHub で見る

しばらく使われていないと、開くまで数秒かかることがあります。

なぜ作ったか

動画を分析しようとすると、再生回数だけ見ても、その数字が多いのか少ないのかが分かりません。チャンネルの規模に対してどうなのか、同じチャンネルの他の動画と比べてどうなのかを、そのつど手で数えていました。

URL を貼れば必要な数字が並ぶ状態にしたかったので、YouTube Data API v3 を叩く画面を作りました。

どう作ったか

動画の分析（再生回数・高評価・コメント・エンゲージメント率）と、チャンネルの分析（登録者・投稿頻度・直近動画の一覧）の2本立てです。結果は CSV と JSON で書き出せます。

技術的に決めたことが2つあります。

API キーの設計を、公開直前に1つ覆した

API キーは、まず自分のものにしない設計にしました。キーは画面のサイドバーから入力する方式にして、訪問者は自分のキーを入れて使う想定でした。自分のキーを公開アプリに埋めると、他人が使った分まで自分の利用枠から引かれます。

この判断を、今回のホスティング移行にあわせて1つ覆しました。スリープを直しても、キーを持っていない訪問者には空の画面のままで、「実際に動くものを触れる」というポートフォリオの目的を満たせていませんでした。そこでお試し用のキーを Google Cloud の Secret Manager に置き、訪問者は何も入力せずに触れるようにしました。自分のキーを入れる欄は残してあり、入れればそちらが優先されます。

他人の利用分が自分の枠から引かれるという元の判断は、今も事実として正しいです。承知のうえで、上限のある枠を開放した、という整理にしました。YouTube Data API の無料枠は1日10,000ユニットです。検索1回が101ユニットなので、お試し用のキーは1日およそ99回の検索で使い切る計算になります。ハンドルからチャンネルを引く処理は1ユニットです。上限に達しても課金は発生せず、翌日まで使えなくなるだけです。

同じ問い合わせを繰り返さない

取得した結果は SQLite に貯めて、同じ URL なら再利用します。API の利用枠は1日あたりで決まっているので、これがないとすぐ上限に当たります。

詰まった点と、直したこと

このツールで一番手を入れたのは、新しい機能ではなく、公開の設計を変えたことで新しく生まれた穴と、手元で自分だけが使う前提のまま残っていた部分でした。

サーバーにキーを置いた直後、そのキーがエラー画面に出ていた

キーをサーバー側に置いた最初の動作確認で、チャンネル URL の解析に失敗してエラーが出ました。そのエラー本文に API キーが平文で表示されていました。

仕組みはこうでした。google-api-python-client が投げる例外は、問い合わせたリクエスト URL をメッセージ本文に含みます。その URL には key= が付いています。アプリ側は「チャンネル取得エラー: 〜」と日本語を付けて投げ直していて、エラーを画面用に整える処理（utils/errors.py）は「日本語が含まれていればそのまま出す」というルールだったので、キー入りの URL がそのまま素通りしていました。

訪問者が壊れた URL をわざと貼るだけでキーを抜ける状態でした。対処は同じ関数の1箇所で、画面に出す前に API キーとリクエスト URL を伏せるようにしました。すべてのエラー表示がこの関数を通っていたので、1箇所で塞げました。露出したキーは削除して作り直しました。

直近動画が2本しか取れていなかった

公開したあと、動画が6,100本あるチャンネルを分析してみると、画面の設定は20本のはずが、直近動画が2本しか出てきませんでした。

原因は取得方法でした。search の API は、チャンネルを指定しても直近の数本しか返さないことがあります。チャンネルの「アップロード済み再生リスト」を辿る方式に変えました。指定した本数がそのまま取れるようになり、あわせて消費する API の枠が34分の1になりました。チャンネル分析1回あたり102ユニットだったのが3ユニットで済むようになり、お試し用のキーで1日にできる分析は約98回から約3,300回に増えました。

お試し用のキーを置く判断をした日に、そのキーの寿命を34倍にする修正が見つかった格好になりました。

取得を直したら、隠れていたバグが2つ出てきた

直近動画が2本から20本になった瞬間、それまで一度も動いたことのないコードが動き始めて、2つ壊れました。

1つ目は if len(直近動画) > 5: という条件の内側にあった処理です。2本しか取れていなかった間はこの行に一度も到達していませんでした。中身は公開日を文字列として切り出す書き方になっていましたが、実際の値は日時型だったため例外になりました。

2つ目はグラフを描く処理です。ずっと「アップロード日時データがありません」と表示していましたが、原因は同じく日時型を文字列として扱っていたことでした。こちらは except: で例外を握りつぶし、全件を静かに捨てていました。エラーは一度も出ず、データが無いだけの正常な画面に見えていました。

「データがありません」という表示が、取得の失敗を隠していました。直したら、日別アップロード数の棒グラフが正しく出るようになりました。

ライブラリの版を固定したら、3箇所が表示されなくなった

再ビルドのたびに違う版が入らないよう、動作確認した版（Streamlit 1.64.0）に固定しました。すると st.image に渡していた use_column_width=True が3箇所でエラーになりました。この引数はもう存在しません。width="stretch" に書き換えました。それまでは版を「これ以上」としか指定していなかったので、いつ入れ直すかによって動いたり動かなかったりする状態でした。固定して初めて、どの版で動くのかが決まりました。

版のログを遡ると、もう1つの引数も公式に「2025年12月31日以降に削除」と告知されていて、その期限をすでに9か月過ぎていました。まだ動いてはいましたが、次に版を上げれば同じことが起きるので、こちらも4箇所を新しい書き方に変えました。

「チャンネル ID を取得する関数」が、ID を取得していなかった

youtube.com/@名前 形式の URL を貼るとチャンネルが分析できませんでした。調べると get_channel_id_from_handle という名前の関数はありましたが、中身は URL を組み立てて返すだけで、チャンネル ID は返していませんでした。「実際のチャンネル ID 取得には YouTube API が必要」というコメントが残る、作りかけの状態でした。今の YouTube は @名前 形式の URL が主流なので、訪問者がチャンネルページからコピーしてくる URL はまずこれになります。forHandle パラメータで API に問い合わせ直す処理を実装しました。

出典を示せない数字が2種類、画面に混ざっていた

1つは他チャンネルとの比較機能。「同じジャンルの平均」と並べて表示していましたが、その平均値がどこから来た数字なのか説明できませんでした。実在するデータを集めて比較しているわけではなかったので、機能ごと削除しました。

もう1つは「高評価率 4%・コメント率 0.5%」という目安値。これは比較の基準として実際に役に立ちますが、出典のある統計ではありません。こちらは残して、画面に「出典のある統計ではない」と書きました。

消したものと残したものの違いは、その数字が何なのかを画面で説明できるかどうかにしました。

キャッシュが訪問者全員で共有されていた

取得結果を貯める仕組みは、手元で1人で使う前提で書いていました。公開するとアプリを開いた全員が同じ貯蔵庫を読むことになります。別のブラウザから開いて、他方で取得したデータが読めることを実際に確認しました。

扱っているのは YouTube の公開データなので内容自体に問題はありません。ただ「表示された数字が自分のキーで取ったものとは限らない」のは利用者が知っておくべきことなので、README に仕様として明記しました。合わせて、同時アクセスで書き込みが競合しないよう SQLite の設定を変えています。

エラーが英語のまま出ていた

API から返る例外を、そのまま画面に流していた箇所が4つ。何が起きたのか利用者に伝わらないので、日本語のメッセージに変換する処理を通しました。

ここから学んだこと

設計を変えると、それまで無害だった箇所が危険になります。今回いちばん効いた学びはこれでした。

キーを画面から入力させていた間、エラーメッセージにキーが混ざっても、それは訪問者自身のキーでした。サーバー側にキーを置いた瞬間、同じコードパスが自分のキーを漏らす経路に変わっていました。コードは1行も変えていないのに、そこを通るものの意味が変わっていました。設計を変えるときは、変えた場所だけでなく、変えていない場所が何を通しているかも見直す必要があります。

もう1つは、公開したときから変わらない学びです。自分用のツールを公開用に変えるとき、いちばん手を入れたのは「数字の出どころ」でした。自分で使っている間は、どの数字が実測でどれが仮置きかを覚えています。他人が見る画面では、覚えていることは何の役にも立ちません。説明できない数字は、消すか、説明を添えるかの二択になりました。

「データがありません」という正常そうな表示が、取得の失敗を隠していたのも同じ根っこでした。画面が静かなときほど、本当に無いのか取得できていないだけなのかを疑うようにしています。

公開について

Google Cloud の Cloud Run で公開中です。元は Streamlit Cloud の無料枠で動かしていましたが、しばらくアクセスがないとスリープし、再開には100秒以上かかるうえ起動を促すボタンを押す必要がありました。企業リサーチシステムを移したときと同じ理由で、こちらに移しました。

使うには本来 YouTube Data API v3 のキーが要りますが（無料枠があります）、お試し用のキーを Google Cloud の Secret Manager に用意したので、キー入力なしでそのまま動きます。自分のキーを画面から入れれば、そちらが優先して使われます。お試し用のキーは訪問者全員で共有しているので、アクセスが集中した日は上限に達して翌日まで使えなくなることがあります。

しばらくアクセスがないとアプリは止まり、次に開いたときに起動し直します。17分22秒アクセスがなかったあとに開いたところ、サーバーが応答するまで実測で4.14秒でした（サーバー側のログで「新しい台が起動した（理由: AUTOSCALING）」ことを確認したうえでの数字です）。企業リサーチシステムの実測1.9〜4.4秒と同じ範囲に収まりました。
